## 2. Scenario: A Social Media Application

You have been hired to create a simple database for a social media application.

The application allows users to:
- Create accounts.
- Publish posts.
- Like posts published by other users.

The database will contain three tables:

| Table | Purpose |
|---|---|
| Users | Stores user account information. |
| Posts | Stores posts published by users. |
| Likes | Records which users like which posts. |

### Understanding the Relationships

- One user can publish many posts.
- One user can like many posts.
- One post can receive likes from many users.

The relationship between Users and Posts is one-to-many.

The relationship between Users and Posts through Likes is many-to-many.

The Likes table is called a **junction table** because it connects Users and Posts.

## 4. Step 2: Create the Schema SQL File

1. In RStudio, select **File → New File → Text File**.
2. Save the file as:

   `social_media_schema.sql`

3. Enter the SQL code below.

### SQL Schema Code

```sql
-- =========================================
-- SOCIAL MEDIA DATABASE
-- PostgreSQL Schema
-- =========================================

-- STEP 1: Create a schema
CREATE SCHEMA IF NOT EXISTS social_app;


-- STEP 2: Create the Users table
CREATE TABLE social_app.users (
    user_id INTEGER GENERATED BY DEFAULT AS IDENTITY,
    username VARCHAR(50) NOT NULL UNIQUE,
    email VARCHAR(100) UNIQUE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT pk_users
        PRIMARY KEY (user_id)
);


-- STEP 3: Create the Posts table
CREATE TABLE social_app.posts (
    post_id INTEGER GENERATED BY DEFAULT AS IDENTITY,
    user_id INTEGER NOT NULL,
    content TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT pk_posts
        PRIMARY KEY (post_id),

    CONSTRAINT fk_posts_users
        FOREIGN KEY (user_id)
        REFERENCES social_app.users(user_id)
);


-- STEP 4: Create the Likes junction table
CREATE TABLE social_app.likes (
    user_id INTEGER NOT NULL,
    post_id INTEGER NOT NULL,
    liked_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT pk_likes
        PRIMARY KEY (user_id, post_id),

    CONSTRAINT fk_likes_users
        FOREIGN KEY (user_id)
        REFERENCES social_app.users(user_id),

    CONSTRAINT fk_likes_posts
        FOREIGN KEY (post_id)
        REFERENCES social_app.posts(post_id)
);


-- STEP 5: Confirm that the tables exist
SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'social_app'
ORDER BY table_name;
```

4. Save the file using **Ctrl + S**.

## 5. Step 3: Understand the SQL Commands

Before executing the code, understand what each part does.

| SQL command or feature | Explanation |
|---|---|
| `CREATE SCHEMA` | Creates a namespace inside the current database. |
| `CREATE TABLE` | Creates a table. |
| `INTEGER` | Stores whole numbers. |
| `VARCHAR(50)` | Stores text up to 50 characters. |
| `TEXT` | Stores text of variable length. |
| `NOT NULL` | Prevents a column from being left empty. |
| `UNIQUE` | Prevents duplicate values in a column. |
| `PRIMARY KEY` | Uniquely identifies a row. |
| `FOREIGN KEY` | Connects a column to a key in another table. |
| `IDENTITY` | Allows PostgreSQL to generate IDs automatically. |
| `DEFAULT CURRENT_TIMESTAMP` | Automatically records the current date and time. |

### Understanding the Composite Primary Key

In the Likes table, the primary key is:

```sql
PRIMARY KEY (user_id, post_id)
```

This is called a **composite primary key** because it consists of two columns.

It prevents the same user from liking the same post more than once.

However, the same user can like different posts, and the same post can be liked by different users.

## 6. Step 4: Create an R Script to Connect to PostgreSQL

Since the practical is being completed in Posit Cloud, R can be used to connect to PostgreSQL and execute the SQL file.

### 4.1 Create the R Script

1. Select **File → New File → R Script**.
2. Save the file as `run_schema.R`.

### 4.2 Install the Required Packages

Run the following commands in the R console:

```r
install.packages(c("DBI", "RPostgres"))
```

You only need to install these packages once per environment.

Load the packages in your script:

```r
library(DBI)
library(RPostgres)
```

### 4.3 Connect to PostgreSQL

Configure the connection details using environment variables provided by your lecturer or database administrator.

```r
con <- dbConnect(
  RPostgres::Postgres(),
  host = Sys.getenv("PGHOST"),
  port = as.integer(Sys.getenv("PGPORT", "5432")),
  dbname = Sys.getenv("PGDATABASE"),
  user = Sys.getenv("PGUSER"),
  password = Sys.getenv("PGPASSWORD"),
  sslmode = "require"
)
```

Do not publish your database password in a shared script or repository.

### 4.4 Read and Execute the SQL File

Add the following code after the connection code:

```r
# Read the SQL file
sql_text <- readLines(
  "social_media_schema.sql",
  warn = FALSE
)

sql_text <- paste(sql_text, collapse = "\n")

# Split the file into SQL statements
statements <- strsplit(
  sql_text,
  ";",
  fixed = TRUE
)[[1]]

# Execute each SQL statement
for (statement in statements) {

  statement <- trimws(statement)

  if (nchar(statement) == 0) next

  if (grepl("^SELECT\\b", statement,
            ignore.case = TRUE)) {

    print(dbGetQuery(con, statement))

  } else {

    dbExecute(con, statement)

  }
}

# Close the database connection
dbDisconnect(con)
```

This simple execution script is suitable for the SQL statements in this practical. It assumes semicolons are used only to terminate statements, not inside quoted strings or procedural blocks.

### 4.5 Execute the R Script

1. Save `run_schema.R`.
2. Ensure that `social_media_schema.sql` is in the same project directory.
3. Click **Source** in the RStudio script editor.
4. Check the Console for the results.

Expected table names:

```text
likes
posts
users
```

If an error occurs, check your PostgreSQL connection details and database permissions.

## 9. Step 7: Practise More Advanced Queries

### Activity 1: Display Each Post and Its Likes

```sql
SELECT
    users.username,
    posts.content,
    likes.liked_at
FROM social_app.likes AS likes
JOIN social_app.users AS users
    ON likes.user_id = users.user_id
JOIN social_app.posts AS posts
    ON likes.post_id = posts.post_id;
```

### Activity 2: Count Likes per Post

```sql
SELECT
    posts.post_id,
    posts.content,
    COUNT(likes.user_id) AS total_likes
FROM social_app.posts AS posts
LEFT JOIN social_app.likes AS likes
    ON posts.post_id = likes.post_id
GROUP BY posts.post_id, posts.content
ORDER BY posts.post_id;
```

The `LEFT JOIN` ensures that posts with zero likes are also displayed.

### Activity 3: Find Users Who Have Not Liked Any Posts

```sql
SELECT
    users.user_id,
    users.username
FROM social_app.users AS users
LEFT JOIN social_app.likes AS likes
    ON users.user_id = likes.user_id
WHERE likes.user_id IS NULL;
```

### Activity 4: Test Referential Integrity

Try inserting a like for a nonexistent post:

```sql
INSERT INTO social_app.likes (user_id, post_id)
VALUES (1, 9999);
```

PostgreSQL should reject this command because Post 9999 does not exist.

This demonstrates how a foreign key protects relationships between tables.

### Activity 5: Test the Composite Primary Key

Try inserting the same user-post pair twice:

```sql
INSERT INTO social_app.likes (user_id, post_id)
VALUES (1, 2);

INSERT INTO social_app.likes (user_id, post_id)
VALUES (1, 2);
```

The second insert should fail because the composite primary key prevents duplicate user-post pairs.
